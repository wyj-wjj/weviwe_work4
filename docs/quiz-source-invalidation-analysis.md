# AI 候选题来源失效问题分析与改进方案

记录日期：2026-06-24

## 一、问题背景

管理员在后台发布一次“大更新”后，系统会基于该发布版本生成 AI 候选测试题，并创建对应的专题测验包。

实际操作中可能出现以下误操作场景：

1. 管理员误发布了一个错误的大更新。
2. AI 候选题已经生成，题目状态为“待审核”。
3. 管理员随后马上将该内容下线，或者修正内容后重新发布新版本。
4. 专题测验包显示为“停用”，但包内题目仍然显示为“待审核”。
5. 后台仍然可以对这些题目进行“审核通过并启用 / 驳回 / 启用”等操作。
6. 某些情况下，“驳回”按钮出现偶发无法点击或操作体验不稳定的问题。

该问题表面上像是前端按钮问题，但本质是内容版本、专题包、测试题之间的状态联动规则不完整。

## 二、当前现象分析

当前系统里至少存在三套状态：

| 对象 | 主要状态 | 当前问题 |
| --- | --- | --- |
| 内容 | 草稿、已发布、已下线、当前版本 | 内容下线或版本更新后，没有统一通知题目进入失效态 |
| 专题测验包 | 启用、停用 | 内容下线时专题包可以停用，但只影响包本身 |
| 测试题 | 待审核、已通过、已驳回、启用、禁用、待复核 | 题目仍然保留原审核状态，且后台仍允许操作 |

目前内容下线后，系统已经能把相关专题测验包置为停用，但没有同步处理包内题目，所以会出现：

```text
专题包：停用
题目审核状态：待审核
题目启用状态：仍可被管理员操作
```

这会让管理员误以为：虽然专题包停用了，但题目仍然可以继续审核并上线。

## 三、根因判断

### 1. 系统缺少“题目来源是否有效”的统一判断

AI 生成题并不是独立存在的，它实际绑定了：

- 关联内容 `related_content_id`
- 关联发布版本 `related_version_id`
- 生成批次 `generation_batch_id`
- 可能所属的专题测验包 `quiz_set`

因此，一道题是否可以审核通过或启用，不应只看题目自己的状态，还必须看它的来源是否仍然有效。

建议定义“来源有效”的判断条件：

```text
关联内容存在
且关联内容仍为已发布
且题目绑定版本等于内容当前版本
且如果题目属于专题包，则专题包仍然有效
```

只要任一条件不满足，该题目就应视为“来源已失效”。

### 2. 内容下线只停用了专题包，没有同步处理题目

当前处理逻辑是：

```text
内容下线
  -> 内容状态改为 offline
  -> 内容索引失效
  -> 相关专题包停用
```

但缺少：

```text
  -> 关联 AI 候选题自动驳回或禁用
  -> 已通过旧题进入待复核或禁用
  -> 写入明确的失效原因
```

所以题目仍然停留在“待审核”状态。

### 3. 内容重新发布新版本时，旧版本题目存在风险

如果管理员不是直接下线，而是修正后重新发布新版本，例如：

```text
v1：错误大更新，已生成 AI 候选题
v2：管理员修正后重新发布
```

此时 v1 的题目仍然绑定旧版本。如果后台仍允许审核通过，则这些旧版本题目可能被启用。

员工端抽题必须严格要求：

```text
quiz_questions.related_version_id == contents.current_version_id
```

否则会出现“内容已经是 v2，但员工测试题仍来自 v1”的业务风险。

### 4. 后台审核和启用接口缺少来源有效性校验

后台操作不应只依赖前端按钮隐藏。即使前端判断正确，后端仍必须作为最终防线。

当前应补充后端硬约束：

- 来源失效的题目不能审核通过。
- 来源失效的题目不能启用。
- 来源失效的题目如果已经启用，应被自动禁用或标记待复核。
- 对于旧版本 AI 候选题，应禁止继续作为当前有效题目使用。

### 5. “驳回按钮偶发点不了”是状态漂移的交互表现

前端目前主要根据题目的 `review_status` 判断显示“审核通过并启用 / 驳回”按钮。

但按钮没有同时考虑：

- 来源内容是否已下线
- 来源版本是否已经不是当前版本
- 专题包是否已停用
- 当前行是否正在执行审核请求
- 列表刷新过程中状态是否发生变化

因此，当管理员连续进行“下线、刷新、审核、驳回”等操作时，前端容易出现按钮状态与后端真实状态不一致的体验。

该问题不建议只修按钮，而应先修业务状态机，再补前端交互保护。

## 四、建议改进方向

### 1. 增加“来源有效性”判断

建议在后端服务层增加统一判断函数，例如：

```text
is_quiz_question_source_valid(question)
```

判断内容包括：

1. 无关联内容的人工题，可按普通题处理。
2. 有关联内容的题目，必须满足内容已发布。
3. 有关联版本的题目，必须满足该版本是内容当前版本。
4. 属于专题包的题目，专题包必须仍为启用状态。

同时在后台列表返回中增加可展示字段：

```text
source_valid: boolean
source_invalid_reason: string | null
```

示例原因：

- `source_content_offline`：源内容已下线
- `source_version_stale`：源版本已被新版本替代
- `quiz_set_inactive`：专题包已停用

### 2. 内容下线时自动处理关联题目

当内容下线时，应同步处理关联题目：

| 题目类型 | 当前状态 | 建议处理 |
| --- | --- | --- |
| AI 生成题 | 待审核 | 自动驳回 + 禁用 |
| AI 生成题 | 草稿 | 自动驳回或归档 + 禁用 |
| AI 生成题 | 已通过 | 禁用 + 标记待复核 |
| 人工题 | 已通过 | 禁用或标记待复核，视是否强绑定该内容 |

推荐写入明确原因：

```text
源内容已下线，AI 候选题已自动驳回。
```

这样后台就不会继续展示一个“看似还能审核”的旧候选题。

### 3. 内容发布新版本时处理旧版本题目

当内容发布新版本时，应处理旧版本题目：

| 场景 | 建议处理 |
| --- | --- |
| 旧版本 AI 候选题仍待审核 | 自动驳回 + 禁用 |
| 旧版本已通过题目 | 禁用 + 标记待复核 |
| 新版本为中更新 | 标记相关题目待复核 |
| 新版本为大更新 | 创建新候选题或新专题包，旧版本题目不得直接沿用 |

推荐写入原因：

```text
源版本已被 v2 替代，旧版本候选题已失效。
```

### 4. 审核和启用接口增加后端防线

后台接口必须增加校验：

```text
POST /api/admin/quiz-questions/{id}/approve
POST /api/admin/quiz-questions/{id}/enable
```

如果题目来源已失效，应返回明确错误，例如：

```json
{
  "code": "quiz_source_invalid",
  "message": "源内容已下线或源版本已失效，不能审核通过或启用该题目。"
}
```

这可以避免前端状态异常、多人同时操作、页面未刷新等情况下产生脏数据。

### 5. 员工端抽题增加版本一致性过滤

员工端测试题查询必须同时满足：

```text
题目已启用
题目已审核通过
题目不需要复核
题目未过期
当前用户有权限查看
关联内容已发布
题目绑定版本等于内容当前版本
```

关键规则：

```text
如果 quiz_questions.related_version_id 不为空，
则必须等于 contents.current_version_id。
```

这样可以避免旧版本题目在内容更新后继续被员工抽到。

### 6. 前端后台展示来源状态

测试题后台列表建议增加“来源状态”展示：

| 来源状态 | 展示文案 | 操作建议 |
| --- | --- | --- |
| 有效 | 来源有效 | 可审核、可启用 |
| 内容下线 | 源内容已下线 | 禁止审核通过，建议显示已自动驳回 |
| 版本失效 | 源版本已失效 | 禁止审核通过，建议重新生成题目 |
| 专题包停用 | 专题包已停用 | 禁止作为专题题上线 |

来源失效时，前端应：

- 隐藏或禁用“审核通过并启用”。
- 隐藏或禁用“启用”。
- 展示明确原因。
- 保留“查看 / 编辑 / 已驳回记录”等安全操作。

### 7. 前端按钮增加行级操作保护

为解决“驳回按钮偶发点不了”或重复点击问题，建议前端增加行级 pending 状态：

```text
pendingActionQuestionId
```

当某一行正在审核、驳回、启用、禁用时：

- 只禁用当前行按钮。
- 按钮显示“处理中...”。
- 请求完成后重新加载列表。
- 如果后端返回来源失效，展示准确错误文案。

这样可以减少连续点击、列表刷新、状态变化导致的交互不稳定。

## 五、推荐最终状态流

### 场景 A：错误大更新发布后马上下线

```text
发布 v1 大更新
  -> AI 生成候选题
  -> 创建专题测验包

管理员发现错误并下线内容
  -> 内容 offline
  -> 专题包 inactive
  -> v1 待审核 AI 候选题 rejected + disabled
  -> 写入原因：源内容已下线，候选题已自动驳回
```

此时后台应看到：

```text
专题包：停用
题目：已驳回 / 禁用
来源状态：源内容已下线
操作：不能审核通过，不能启用
```

### 场景 B：错误大更新发布后马上修正并发布 v2

```text
发布 v1 大更新
  -> AI 生成候选题

管理员修正内容并发布 v2
  -> v1 候选题自动失效
  -> v1 专题包停用
  -> v2 根据更新级别重新生成或复核题目
```

此时后台应看到：

```text
v1 题目：源版本已失效，不能审核通过
v2 题目：按新版本重新审核
```

员工端只能抽到：

```text
绑定当前版本 v2 的有效题目
```

## 六、验收标准

后续实现时，建议至少覆盖以下验收点：

1. 发布大更新并生成 AI 候选题后，下线该内容，候选题自动变为已驳回或来源失效状态。
2. 来源已失效的候选题不能审核通过。
3. 来源已失效的候选题不能启用。
4. 下线内容对应的专题测验包保持停用。
5. 重新发布新版本后，旧版本候选题不能被员工抽到。
6. 员工端抽题严格校验 `related_version_id == current_version_id`。
7. 后台题目列表能看到来源状态和失效原因。
8. 前端审核、驳回、启用、禁用按钮有行级 loading，不再出现操作状态漂移。
9. 后端测试覆盖内容下线、版本替换、审核通过、启用、员工抽题几个关键路径。

## 七、实施优先级建议

建议按以下顺序改：

1. 后端增加来源有效性判断。
2. 员工端抽题增加版本一致性过滤。
3. 审核通过和启用接口增加来源失效拦截。
4. 内容下线和发布新版本时自动处理旧题目。
5. 后台列表返回来源状态和失效原因。
6. 前端展示来源状态，并禁用危险操作。
7. 前端增加行级 pending 状态，优化驳回按钮体验。

其中第 1 至第 4 项是数据安全底线，应优先实现；第 5 至第 7 项是后台体验优化，但也建议同步完成，避免管理员继续误判。
