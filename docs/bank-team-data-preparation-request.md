# 银行组统一口径系统数据准备说明

## 一、背景与目标

为支持银行组同事在日常沟通、项目推进、资料答复、内部同步等场景中保持信息一致，现需整理一批可用于系统初始化和后续维护的标准数据。

本次数据准备目标是形成一套“可发布、可追溯、可权限区分、可持续更新”的银行组统一口径数据包，用于支撑以下工作：

1. 银行组内部及时同步最新业务口径。
2. 员工对外输出时使用统一、准确、可控的标准表达。
3. 对高频问题、关键流程、敏感边界形成可查询的标准依据。
4. 对重要更新配套巩固测试，帮助员工确认理解是否到位。

请数据部门及相关业务负责人按本文档要求准备数据。

## 二、总体交付要求

请以结构化表格为主进行交付，原始依据文件作为附件一并提供。

交付内容应包含：

1. 标准话术数据。
2. 最新必读数据。
3. 核心基础话术数据。
4. 历史问答样本。
5. 禁用表达与风险边界。
6. 巩固测试题库。
7. 原始依据文件。

每条数据均需明确：

- 业务分类。
- 适用场景。
- 权限级别。
- 生效状态。
- 版本信息。
- 内容负责人。
- 来源依据。

无法确认有效性、权限范围或来源依据的数据，请单独标记为“待确认”，不要混入正式数据。

### 新权限模型下所有 Excel 都需要关注的字段

当前系统已经引入“部门范围 + 账号等级”的权限模型，因此所有正式数据都应同时标明以下两个维度：

| 字段 | 填写值 | 说明 |
| --- | --- | --- |
| 可见范围 | 全公司通用 / 限定部门 | 表示横向可见范围。银行组内部资料通常建议填写“限定部门”。 |
| 限定部门 | 如：银行组 | 仅当“可见范围=限定部门”时填写；“全公司通用”时留空。 |
| 权限级别 | 通用级 / 全量级 / 待确认 | 表示敏感等级。通用级是低敏内容，全量级是更完整、更敏感或内部内容。 |
| 生效状态 | 当前有效 / 已失效 / 待确认 | 只有当前有效且确认可用的数据才建议进入正式发布流程。 |

这几个字段的关系不要混淆：

```text
全公司通用 / 限定部门 = 内容横向可见范围
通用级 / 全量级 = 内容纵向敏感等级
```

例如：

| 可见范围 | 权限级别 | 含义 |
| --- | --- | --- |
| 全公司通用 | 通用级 | 所有员工都可见的基础内容 |
| 全公司通用 | 全量级 | 全量权限员工和管理员可见的跨部门敏感内容 |
| 限定部门=银行组 | 通用级 | 银行组内普通员工也可见的部门内容 |
| 限定部门=银行组 | 全量级 | 银行组内全量权限员工和管理员可见的部门敏感内容 |

## 五、可见范围与权限级别说明

所有数据必须同时标注“可见范围”和“权限级别”。

### 1. 可见范围

| 可见范围 | 说明 | 示例 |
| -------- | ---- | ---- |
| 全公司通用 | 不按部门限制，只按权限级别过滤 | 全公司都需要知道的基础合规提醒 |
| 限定部门 | 只对指定部门内员工可见，并继续按权限级别过滤 | 银行组内部资料清单、银行沟通口径 |

选择“限定部门”时，必须填写“限定部门”字段。例如：

```text
可见范围：限定部门
限定部门：银行组
```

### 2. 权限级别

| 权限级别 | 说明                                                           | 示例                                                         |
| -------- | -------------------------------------------------------------- | ------------------------------------------------------------ |
| 通用级   | 银行组普通员工可查看、可学习、可用于日常对外或内部沟通         | 基础业务介绍、常规对外表达、一般资料要求                     |
| 全量级   | 仅完整权限员工和管理员可查看，包含更完整、更敏感或更内部的信息 | 内部判断依据、投融资细节、敏感风险边界、非公开客户或项目背景 |

无法判断可见范围或权限级别的数据，请标记为“待确认”，并由业务负责人确认后再进入正式数据。

## 六、脱敏要求---可以根据公司具体要求决定是否脱敏

交付数据必须先完成脱敏处理。

以下信息不得直接进入正式数据：

1. 个人手机号、身份证号、银行卡号、私人邮箱等个人敏感信息。
2. 未授权披露的客户名称、银行名称、联系人姓名。
3. 未公开合同金额、账户信息、协议条款、授信细节。
4. 未经确认可共享的项目敏感信息。
5. 与当前业务口径无关的内部讨论、个人判断或过程性争议内容。

脱敏方式：

| 原始信息     | 脱敏后写法                           |
| ------------ | ------------------------------------ |
| 具体客户名称 | 某客户 / 某银行 / 某项目             |
| 具体联系人   | 客户联系人 / 银行联系人              |
| 具体金额     | 金额区间 / 示例金额 / 按实际审批为准 |
| 具体项目名称 | 某储能项目 / 某光伏项目              |
| 具体合同编号 | 合同编号已脱敏                       |

如某条内容必须保留真实名称或真实数值，请单独标记，并说明保留原因和可见权限。

## 七、来源依据要求---首批数据可以不需要，后续发布更新维护的信息最好包含

每条正式数据均需有来源依据。

可接受的来源依据包括：

- 公司制度。
- 部门正式通知。
- 已确认的会议纪要。
- 审批记录。
- 正式邮件。
- 已发布模板。
- 经业务负责人确认的标准口径。

不宜作为正式依据的材料：

- 个人聊天记录中未经确认的说法。
- 临时讨论意见。
- 无负责人确认的口头表达。
- 来源不明的旧文档。
- 与当前执行口径不一致的历史材料。

## 八、版本与更新要求---用于后续管理员维护，目前首批数据不考虑

每条内容应保留版本信息。

填写规则：

| 字段     | 要求                                         |
| -------- | -------------------------------------------- |
| 版本号   | 首次提供为 v1，后续每次实质调整递增为 v2、v3 |
| 生效时间 | 标明该版本开始执行的时间                     |
| 失效时间 | 如果被新口径替代，应标明失效时间             |
| 更新说明 | 简要说明本次变更原因                         |
| 更新级别 | 小更新 / 中更新 / 大更新                     |

当内容发生调整时，请不要直接覆盖旧内容，应新增一个版本，并说明变更点。

## 九、质量检查要求

交付前请完成以下检查：

| 检查项     | 要求                             |
| ---------- | -------------------------------- |
| 内容完整性 | 必填字段已填写完整               |
| 权限级别   | 每条数据均已标注通用级或全量级   |
| 来源依据   | 每条正式数据均有明确来源         |
| 脱敏处理   | 敏感信息已删除、替换或单独标记   |
| 表达一致性 | 同一问题不存在互相冲突的多个口径 |
| 生效状态   | 已区分当前有效、已失效、待确认   |
| 负责人     | 每条内容有可追溯负责人           |

如发现同一事项存在多个版本或多个说法，请不要自行合并，应全部列出，并标记“需业务确认”。

## 十、交付方式

请将整理好的数据包压缩后交付。

压缩包命名格式：

```text
银行组统一口径数据包_部门名称_YYYYMMDD.zip
```

交付时请同时说明：

1. 本次交付包含哪些文件。
2. 哪些内容已确认可正式使用。
3. 哪些内容仍待业务负责人确认。
4. 是否存在无法脱敏但必须保留的信息。
5. 后续维护联系人。

## 十一、联系人信息

请在数据包中附一份联系人说明，包含：

| 角色           | 姓名/部门 | 职责                           |
| -------------- | --------- | ------------------------------ |
| 数据整理负责人 |           | 负责本次数据包整理             |
| 业务口径确认人 |           | 负责确认内容是否为当前有效口径 |
| 权限确认人     |           | 负责确认通用级/全量级划分      |
| 后续维护联系人 |           | 负责后续版本更新与问题反馈     |

## 十二、交付确认

数据包交付后，将按照以下顺序进行确认：

1. 检查文件是否齐全。
2. 检查字段是否完整。
3. 检查权限级别是否已标注。
4. 检查敏感信息是否已脱敏。
5. 抽查来源依据是否清晰。
6. 将“待确认”内容单独反馈给对应负责人。
7. 确认可用数据后进入系统初始化流程。

请确保交付数据具备正式使用条件，避免将未经确认、来源不明、权限不清或未脱敏内容混入正式数据。
