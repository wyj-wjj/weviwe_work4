# 巩固测试题目抽取策略方案

## 背景

当前员工端“巩固测试”的“重新抽题”会重新请求 `GET /api/app/quiz`，但后端并不是随机抽题，而是按固定排序取前 10 道：

- 跟进最新：`priority desc`、关联内容发布时间倒序、题目 `id asc`。
- 复习旧内容：`priority desc`、题目更新时间倒序、题目 `id asc`。

因此，只要题库、权限、部门范围和排序字段不变，重复点击“重新抽题”大概率会得到同一批题。这个现象不是前端按钮失效，而是后端抽题策略本身偏“固定优先级列表”。

## 目标

优化后的策略应同时满足两个目标：

1. 保留“跟进最新”的业务导向：重要更新、新发布内容、较高优先级题目仍然排在前面。
2. 让“重新抽题”有真实变化：在同一优先级、同一内容批次内随机抽取，避免永远命中同几道题。

本方案不新增员工答题历史、分数、排行、错题本或统计表，继续符合 MVP 边界。

## `priority` 字段说明

`priority` 是 `quiz_questions` 表已有字段，由迁移 `0006_quiz_ai_generation_sets` 增加：

- 类型：整数。
- 非空。
- 默认值：`0`。
- 每道题都有该字段。

当前等级含义：

| priority | 含义 | 来源 |
| --- | --- | --- |
| `100` | 大更新专题题，最优先进入巩固测试 | 内容版本为 `major`，或 `quiz_action=generate_pack` |
| `50` | 中更新复核题，次优先进入巩固测试 | 内容版本为 `medium`，或 `quiz_action=review_related` |
| `0` | 普通题，作为常规练习和补足题量 | 人工题默认值、小更新题、无更新等级题 |

后台“测验题管理”已经暴露“抽题优先级”字段，管理员可手动调整人工题或已有题目的优先级。未填写时按 `0` 处理。

## 基础过滤规则

无论是否随机，员工端题目候选集必须先经过后端过滤。只有满足以下条件的题目才能进入抽题池：

- `status=enabled`。
- `review_status=approved`。
- `needs_review=false`。
- `expires_at` 为空或尚未过期。
- 题目 `permission_level` 在当前用户可见权限内。
- 如果题目绑定了内容，关联内容必须仍为已发布。
- 如果题目绑定了版本，`related_version_id` 必须等于关联内容当前版本。
- 如果内容限定部门，当前用户必须属于该部门；全公司内容按现有权限级别可见。

这些过滤仍以后端为准，前端不参与安全判断。

## 推荐抽题策略

### 总体思路

后端不做全局随机，而是做“分层优先 + 层内随机”：

```text
先按业务重要性分层：
priority 越高越靠前
关联内容越新越靠前

再在同一层内随机：
同 priority + 同内容版本批次的题目打散
```

这样可以保证大更新题、中更新题、最新内容题仍然更容易出现，同时“重新抽题”不会每次固定返回同一批 `id` 最小的题。

### 分层维度

建议每道候选题计算一个抽题分组 key：

```text
抽题分组 = priority + related_version_id 或兜底批次
```

分组规则：

1. 有 `related_version_id` 的题：使用 `related_version_id` 作为内容批次。
2. 没有 `related_version_id` 但有关联内容的题：使用关联内容当前版本或发布时间作为批次。
3. 完全没有关联内容的人工通用题：放入 `standalone` 普通批次。

组间排序：

```text
priority desc
内容发布时间 desc
批次 id desc 或题目更新时间 desc
```

组内排序：

```text
使用 refresh_seed 稳定随机打散
```

## `refresh_seed` 设计

前端点击“重新抽题”时生成一个随机种子，并传给后端：

```http
GET /api/app/quiz?mode=latest&refresh_seed=172834923
```

后端使用 `refresh_seed` 对同一分组内的题目做稳定洗牌。

稳定洗牌的要求：

- 同一个 `refresh_seed` + 同一候选集，应返回同样的顺序，便于测试和排查。
- 不同 `refresh_seed`，同组内题目顺序应尽量不同。
- 不使用数据库 `ORDER BY RAND()`，避免题量增大后性能不可控。

可选实现方式：

```text
shuffle_key = hash(refresh_seed + question.id)
```

然后在同一分组内按 `shuffle_key` 排序。

## 跟进最新模式

`mode=latest` 仍然是默认模式，目标是让员工优先练最新、最重要的内容。

推荐流程：

1. 按当前用户加载可见题目候选集。
2. 保留现有权限分路逻辑：
   - `general_user` 只取通用级题。
   - `full_user` 和 `admin` 可取通用级与全量级题。
   - 如需最小改动，可先延续当前“优先保留 1 道全量题，再用通用题补足”的策略。
3. 将候选题按 `priority` 和关联内容发布时间分组。
4. 组间按重要性排序。
5. 组内按 `refresh_seed` 随机打散。
6. 从高优先级新批次开始依次取题，直到最多 10 道。

当最高优先级、最新批次的题数量不足 10 道时，再向下一组补足。

## 复习旧内容模式

`mode=review` 的主要目标是复习，不需要强行偏向最新内容。

推荐流程：

1. 继续支持 `category` 分类过滤。
2. 继续执行权限、部门、状态、过期时间和关联内容有效性过滤。
3. 组间按 `priority desc`、题目更新时间或内容发布时间倒序。
4. 组内按 `refresh_seed` 随机打散。

这样复习模式仍会优先出现高优先级题，但同一类、同一批题可以被重新抽到不同组合。

## 题量不足时的预期表现

需要明确接受以下现象：

- 当前用户可见题目总数小于等于 10 道时，“重新抽题”无法换出新题，只可能改变顺序。
- 最高优先级批次刚好只有 10 道且低优先级题不应插入时，题目集合仍可能相同。
- 只有候选题数量明显多于 10 道，且同优先级/同批次内题量足够时，“重新抽题”才会明显换题。

建议前端在按钮旁增加弱提示：

```text
题库较少时可能抽到相同题目
```

## API 调整

后端接口：

```http
GET /api/app/quiz
```

新增可选查询参数：

| 参数 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `mode` | `latest` 或 `review` | `latest` | 已有参数 |
| `category` | string | 空 | 仅复习模式使用，已有参数 |
| `refresh_seed` | string 或 int | 空 | 新增参数，用于同组内稳定随机 |

兼容策略：

- 不传 `refresh_seed` 时，可以使用现有固定排序，保证旧调用兼容。
- 前端“重新抽题”应始终传新的 `refresh_seed`。
- 首次进入页面也可以传一次 `refresh_seed`，让初始题目同样来自抽样策略。

## 前端调整

员工端 `QuizPage`：

- `loadQuiz()` 每次调用时生成新的 `refresh_seed`。
- 切换模式、切换分类、点击“重新抽题”都应触发新的 `refresh_seed`。
- 提交答案仍按当前页面题目 `id` 提交，不依赖 seed。
- 提交后题目锁定，避免用户提交后重新抽题造成结果和题目不一致。

按钮文案可保留“重新抽题”，并增加弱提示：

```text
题库较少时可能抽到相同题目
```

## 后端实现建议

最小改动建议在 `quiz_service.py` 内实现：

1. 为员工抽题服务增加 `refresh_seed` 参数。
2. 查询候选题时不要只取前 10，道理上应先取一个有限候选窗口，再在窗口内分组随机。
3. 候选窗口建议按性能保守控制，例如每个权限层最多取 50 到 100 道。
4. 对候选题在 Python 层分组和稳定洗牌。
5. 最终返回最多 10 道题。

候选窗口不能无限取全表。推荐先按原有业务排序取一个上限窗口，再做组内随机：

```text
SQL 仍负责权限过滤、状态过滤、过期过滤、关联内容有效性过滤、priority 和发布时间粗排序。
Python 负责在有限候选窗口内分组、洗牌、截取。
```

## 验收测试

### 后端单测

应覆盖以下场景：

1. `priority=100` 的题优先于 `priority=50` 和 `priority=0`。
2. 同一 `priority`、同一 `related_version_id` 下，传不同 `refresh_seed` 返回的题目顺序或组合不同。
3. 同一个 `refresh_seed` 重复请求结果一致。
4. 候选题少于等于 10 道时，返回所有可见题，不报错。
5. `general_user` 不会抽到全量级题。
6. 部门用户不会抽到其他部门限定内容绑定题。
7. 绑定旧版本的题不会因为随机策略绕过当前版本校验。
8. `mode=review&category=...` 仍只返回对应分类内可见题。

### 前端单测

应覆盖以下场景：

1. 首次进入巩固测试会请求 `/app/quiz` 并携带 `mode=latest`。
2. 点击“重新抽题”会再次请求，并携带新的 `refresh_seed`。
3. 切换“复习旧内容”或分类时，会重新生成 seed。
4. 提交后选项锁定，重新抽题前不会混用旧结果。

### 手动验收

准备至少 15 道当前账号可见题，其中同一个 `priority` 和同一个内容版本下至少 12 道。

验收步骤：

1. 用员工账号进入“巩固测试”。
2. 记录首次展示的题目标题或 `id`。
3. 点击“重新抽题”。
4. 确认仍优先展示高 `priority` 和最新内容相关题。
5. 确认同一优先级批次内题目顺序或题目组合发生变化。
6. 切换到“复习旧内容”并选择分类，确认只在该分类内变化。
7. 用题量少于等于 10 道的账号验证：允许结果相同，但页面不报错。

## 不纳入本次方案

- 不记录员工抽过哪些题。
- 不做错题本。
- 不保存答题历史。
- 不做分数、排行、统计。
- 不新增 Redis、Celery 或缓存服务。
- 不引入复杂推荐算法。

后续如果需要“尽量避免同一员工短期内重复题目”，再考虑增加员工抽题历史或轻量本地去重策略。
