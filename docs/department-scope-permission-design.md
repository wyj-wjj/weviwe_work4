# 单部门归属与内容可见范围权限方案

## 1. 背景与目标

当前系统已经具备两级内容权限：

- `general`：通用级内容，通用员工、全量员工、管理员均可见。
- `full`：全量级内容，仅全量员工和管理员可见。

这套模型可以解决“内容敏感度”问题，但不能解决“业务范围”问题。例如储能团队员工即使是通用权限，也不一定应该看到银行团队的通用级内容；银行团队员工也不一定应该看到储能团队内部话术。

因此，下一阶段需要在现有账号等级过滤之上增加“部门归属”维度：

```text
部门范围先限制大范围，账号等级再过滤敏感级别。
```

目标是实现一个简单、清晰、可控的第一版权限模型：

```text
单部门账号 + 全公司通用内容 + 部门限定内容 + 账号等级过滤
```

本方案只定义边界和后续实现原则，不直接修改代码。

## 2. 核心结论

第一版采用“单部门模型”：

- 每个员工账号最多归属一个部门。
- 内容可选择“全公司通用”或“限定某一个部门可见”。
- 全公司通用内容不受部门限制，只受账号等级限制。
- 部门限定内容必须同时满足部门命中和账号等级足够。
- 管理员第一版仍按全局管理员处理，可查看和维护全部内容。

员工端最终可见性判断为：

```text
内容当前有效
AND 部门范围命中
AND 账号内容等级足够
```

展开后为：

```text
content.status = published
AND content.current_version_id 有效
AND (
  content.scope_type = global
  OR content.department_id = user.department_id
)
AND content.permission_level 在 user.content_level 允许范围内
```

其中：

- `scope_type = global` 表示全公司通用。
- `scope_type = department` 表示限定部门。
- `department_id` 表示该内容限定给哪个部门可见。

### 2.1 “全公司通用”和“通用级/全量级”的关系

后续引入部门后，必须保留现有的“通用级/全量级”内容等级，但要把它们从“范围”概念中剥离出来。

推荐统一使用以下口径：

```text
全公司通用 / 限定部门 = 可见范围
通用级 / 全量级 = 敏感等级
```

也就是说：

- `scope_type` 负责“横向范围”：这条内容是全公司可见，还是仅某个部门可见。
- `department_id` 负责“限定到哪个部门”。
- `permission_level` 负责“纵向敏感等级”：这条内容是通用级，还是全量级。
- `user.department_id` 负责账号属于哪个部门。
- `user.content_level` 负责账号最高能看什么敏感等级。

不能把“全公司通用”和“通用级”混为一谈。

```text
全公司通用 = 范围，不代表低敏感。
通用级 = 敏感等级，不代表全公司范围。
```

因此，一条内容可以是：

| 内容可见范围 | 内容敏感等级 | 典型含义 |
| --- | --- | --- |
| 全公司通用 | 通用级 | 所有员工都可以看的基础内容 |
| 全公司通用 | 全量级 | 所有全量员工可看的跨部门敏感内容 |
| 限定部门 | 通用级 | 某部门内所有员工可看的部门内容 |
| 限定部门 | 全量级 | 某部门内全量员工可看的部门敏感内容 |

员工可见性示例：

| 员工账号 | 内容 | 是否可见 | 原因 |
| --- | --- | --- | --- |
| 储能部通用员工 | 全公司通用 + 通用级 | 可见 | 范围命中，等级允许 |
| 储能部通用员工 | 全公司通用 + 全量级 | 不可见 | 范围命中，但等级不足 |
| 储能部通用员工 | 储能部 + 通用级 | 可见 | 部门命中，等级允许 |
| 储能部通用员工 | 储能部 + 全量级 | 不可见 | 部门命中，但等级不足 |
| 储能部通用员工 | 银行团队 + 通用级 | 不可见 | 等级允许，但部门不命中 |
| 储能部全量员工 | 储能部 + 全量级 | 可见 | 部门命中，等级允许 |
| 储能部全量员工 | 银行团队 + 通用级 | 不可见 | 等级允许，但部门不命中 |

后台和前台展示时也应避免使用“通用范围”“全量范围”这类容易混淆的说法。建议固定展示为：

```text
可见范围：全公司通用 / 本部门 / 指定部门
权限等级：通用级 / 全量级
```

发布确认弹窗中也应同时展示这两个维度，避免管理员误以为“全公司通用”就一定是低敏内容，或误以为“通用级”就一定对全公司开放。

## 3. 字段职责边界

后续实现时，各字段职责必须保持单一，不能互相代替。

| 概念 | 职责 | 不应该承担的职责 |
| --- | --- | --- |
| `department` | 组织/业务范围，例如储能部、银行团队 | 不表示敏感等级 |
| `content.scope_type` | 内容可见范围类型：全公司通用或限定部门 | 不表示内容类别 |
| `content.department_id` | 当内容为限定部门时，表示哪个部门可见 | 不表示发布人部门 |
| `permission_level` | 内容敏感度，例如通用级、全量级 | 不表示部门范围 |
| `content_level` | 账号可看的最高内容等级 | 不表示部门归属 |
| `account_type` | 账号身份，例如管理员、全量员工、通用员工 | 不直接承担内容敏感度 |
| `category` | 业务主题，例如消防、并网、银行团队、储能 | 不作为后端权限判断依据 |
| `content_type` | 内容用途，例如最新必读、标准话术、基础话术 | 不作为权限依据 |
| `update_level` | 更新影响等级，小/中/大更新 | 不作为权限依据 |
| `status/current_version_id` | 当前内容是否有效、当前版本是哪一个 | 不表示账号或部门权限 |

尤其要注意：

```text
category 只能用于业务分类和检索辅助，不能当作权限字段。
```

如果把 `category = 银行团队` 当成权限，会出现两个问题：

1. 系统不知道哪些用户属于银行团队。
2. 管理员误填分类时，可能导致权限绕过或误过滤。

## 4. 推荐数据模型

### 4.1 部门表

建议新增独立部门表，而不是用字符串散落在用户表和内容表中。

```text
departments
- id
- name
- code
- is_active
- created_at
- updated_at
```

字段说明：

- `name`：展示名称，例如“储能事业部”“银行团队”。
- `code`：稳定编码，例如 `energy_storage`、`bank_team`，用于导入、测试和未来对接组织系统。
- `is_active`：部门是否启用。停用部门不应再用于新账号或新内容，但历史数据保留。

第一版不做部门树，不做父子部门。

### 4.2 用户表扩展

建议在 `users` 上增加：

```text
department_id nullable
```

规则：

- 普通员工账号建议必须选择部门。
- 管理员账号第一版允许不绑定部门。
- 如果员工账号没有部门，只能看到全公司通用内容，不应看到任何部门限定内容。
- 禁用账号仍按现有逻辑处理，不能登录。

### 4.3 内容表扩展

建议在 `contents` 上增加：

```text
scope_type
department_id nullable
```

可选值：

```text
scope_type = global      全公司通用
scope_type = department  限定部门
```

约束规则：

```text
scope_type = global     -> department_id 必须为空
scope_type = department -> department_id 必须有值
```

不要用“department_id 为空”隐式表示全公司通用。必须显式使用 `scope_type = global`。

原因：

- 管理员漏选部门时，系统可以拦截。
- 后台列表能明确显示“全公司通用”。
- 后续扩展到多部门、部门树、项目组时语义更稳。

### 4.4 内容版本快照

建议同步在 `content_versions` 上保存发布时的可见范围快照：

```text
scope_type
department_id
permission_level
```

原因：

- 历史版本应能看到当时发布时的权限范围。
- 当前内容权限变化不应污染历史审计。
- 测试题和 AI 来源解释需要知道题目生成时所依附的发布版本范围。

员工端和 AI 检索仍只使用当前版本；历史版本只用于后台追溯。

### 4.5 内容切片与索引

建议 `content_chunks` 同步保存：

```text
scope_type
department_id
permission_level
```

Milvus 元数据中也应写入同样字段：

```text
scope_type
department_id
permission_level
is_active
content_id
version_id
chunk_id
```

注意：Milvus 仍然不是权威数据源。即使 Milvus 已按部门过滤，AI 回答前也必须回查 MySQL 再过滤一次。

## 5. 权限判断规则

### 5.1 员工可见内容判断

员工可见一条内容，需要同时满足：

```text
内容状态有效
AND 部门范围命中
AND 内容等级可见
```

其中：

```text
内容状态有效 =
  status = published
  AND current_version_id IS NOT NULL
```

```text
部门范围命中 =
  scope_type = global
  OR (
    scope_type = department
    AND content.department_id = user.department_id
  )
```

```text
内容等级可见 =
  general_user 只能看 general
  full_user 可以看 general + full
  admin 可以看 general + full
```

### 5.2 管理员权限

第一版继续保持：

```text
admin = 全局管理员
```

管理员可以：

- 查看全部部门内容。
- 新建、编辑、发布全部部门内容。
- 管理所有员工账号。
- 管理所有测验题。

第一版暂不做：

- 部门管理员。
- 部门内容审核员。
- 只读管理员。
- 题库管理员。
- 管理员按部门隔离后台数据。

如果后续要做部门管理员，应单独设计后台权限模型，不要把它临时塞进 `department_id`。

### 5.3 员工无部门时的规则

员工账号如果 `department_id` 为空：

- 可以登录。
- 可以查看 `scope_type = global` 且账号等级允许的内容。
- 不能查看任何 `scope_type = department` 的内容。
- AI 问答不能命中任何部门限定内容。
- 巩固测试不能抽到部门限定内容关联题。

这个规则用于兼容历史账号迁移，但不建议长期让员工账号无部门。

## 6. 前台展示规则

员工端不需要暴露复杂权限逻辑，但应让用户理解内容来源范围。

### 6.1 最新必读、标准话术、基础话术

列表和详情建议显示：

```text
可见范围：全公司通用 / 所属部门
权限等级：通用级 / 全量级
更新级别：小更新 / 中更新 / 大更新
```

对于部门限定内容，员工端可以显示为：

```text
可见范围：本部门
```

不一定要暴露具体部门名，避免跨部门信息被过度感知。

### 6.2 AI 问答来源

AI 来源卡片建议显示：

```text
来源标题
内容类型
可见范围
权限等级
更新级别
更新时间
```

但必须保证：

```text
无权来源不进入上下文，也不展示在来源列表中。
```

### 6.3 巩固测试

员工端只看到可答题目，不需要解释为什么没有抽到某些部门题。

如果无可用题，继续使用现有空状态：

```text
暂无可用测验题
```

后续可以在管理员后台增加“员工可见性排查”工具，但第一版不做。

## 7. 后台管理规则

### 7.1 账号管理

新增/编辑员工账号时，管理员需要选择：

```text
账号类型：通用员工 / 全量员工
内容等级：general / full
归属部门：某个启用部门
```

第一版建议：

- 员工账号必须选择部门。
- 管理员账号不在普通账号管理入口维护，保持现有运维逻辑。
- 禁用部门不允许分配给新账号。
- 如果某员工原部门被停用，账号仍保留原部门，但管理员编辑时必须重新选择启用部门。

### 7.2 内容管理

新增/编辑内容时，管理员需要选择：

```text
可见范围：
- 全公司通用
- 限定部门

如果选择限定部门：
- 必须选择一个启用部门
```

发布确认弹窗必须展示：

```text
标题
内容类型
业务分类
可见范围
权限等级
更新级别
发布后影响范围
```

发布确认里的影响范围示例：

```text
全公司通用 + 通用级：所有员工可见
全公司通用 + 全量级：全量员工和管理员可见
储能事业部 + 通用级：储能事业部所有员工可见
储能事业部 + 全量级：储能事业部全量员工可见
```

### 7.3 部门管理

第一版需要一个最小部门管理能力：

- 新建部门。
- 编辑部门名称。
- 启用/停用部门。
- 查看部门列表。

第一版不做：

- 删除部门。
- 部门层级。
- 部门排序。
- 部门负责人。
- 部门管理员。
- 批量导入组织架构。

原因：部门会被用户、内容、历史版本、题库来源引用，删除会破坏历史数据。

## 8. AI 检索规则

AI 问答必须同时应用部门范围和账号等级过滤。

### 8.1 Milvus 召回过滤

向量召回应带上：

```text
permission_level in 当前用户允许等级
AND (
  scope_type = global
  OR department_id = 当前用户 department_id
)
AND is_active = true
```

如果用户没有部门：

```text
只允许 scope_type = global
```

### 8.2 MySQL 关键词召回过滤

MySQL 关键词召回应在 SQL 层过滤：

```text
contents.status = published
AND contents.current_version_id = content_chunks.version_id
AND content_chunks.is_active = true
AND permission_level in 当前用户允许等级
AND 部门范围命中
```

不能先查出全量再在前端过滤。

### 8.3 MySQL 回查二次过滤

无论候选来自 Milvus 还是 MySQL，最终进入回答上下文前必须再次 MySQL 回查并校验：

```text
内容仍发布
仍是当前版本
chunk 仍 active
部门范围仍命中
账号等级仍允许
```

这是防止索引滞后、权限变更、内容下线后仍被 AI 引用的关键防线。

## 9. 测验题规则

测试题也必须遵守部门范围。

### 9.1 绑定内容的题目

如果题目绑定了 `related_content_id`：

```text
题目可见范围跟随关联内容当前权限
```

员工抽题时必须校验：

```text
题目启用
AND 审核通过
AND 无需复核
AND 未过期
AND 题目 permission_level 允许
AND 关联内容仍发布
AND 关联内容当前版本有效
AND 关联内容部门范围命中
AND 关联内容 permission_level 允许
```

如果内容重新发布、下线或范围变更，相关题目仍按已有“来源失效/待复核”机制处理。

### 9.2 未绑定内容的题目

如果后续允许手工创建“不绑定内容”的题目，也需要题目自身具备范围信息。

第一版有两种处理方式：

方案 A：要求所有题目必须绑定内容。
优点是权限简单，题目继承内容范围。缺点是纯通用练习题不方便。

方案 B：给题目也增加 `scope_type` 和 `department_id`。
优点是题目可独立授权。缺点是字段和校验更多。

推荐第一版采用方案 A 的边界：

```text
AI 生成题必须绑定内容版本。
人工题可以暂时保留现状，但如果未绑定内容，则只按题目 permission_level 过滤，不做部门限定。
```

如果业务上需要“某部门专属但不绑定内容的人工题”，再扩展题目自身范围字段。

## 10. 历史版本与权限变更

内容权限范围变化时，必须遵守以下原则：

- 员工端只看当前版本、当前范围。
- AI 只检索当前版本、当前范围。
- 历史版本只供管理员追溯。
- 发布版本应保存当时的 `scope_type`、`department_id`、`permission_level` 快照。
- 旧版本关联题如果不再对应当前版本，应按现有来源失效机制处理。

示例：

```text
v1：储能事业部 + full
v2：全公司通用 + general
```

发布 v2 后：

- 员工端按 v2 的范围判断。
- AI 只检索 v2。
- v1 只在历史版本中可查。
- 绑定 v1 的题目不能继续作为当前有效题直接展示给员工。

## 11. 迁移与默认值策略

为了兼容现有数据，建议迁移时采用保守默认值。

### 11.1 现有用户

现有用户迁移后：

```text
department_id = NULL
```

迁移后表现：

- 账号仍可登录。
- 只能查看全公司通用内容中自己等级允许的内容。
- 管理员应尽快在后台为员工补齐部门。

如果希望不影响当前使用，也可以在迁移时创建一个默认部门：

```text
默认部门：通用部门
```

但这个方案容易把“真实部门未知”和“真的属于通用部门”混淆。推荐先用 `NULL` 表示待补齐。

### 11.2 现有内容

现有内容迁移后推荐：

```text
scope_type = global
department_id = NULL
```

原因：

- 不改变当前可见行为。
- 避免迁移后员工突然看不到原有内容。
- 后续由管理员逐步把部分内容调整为部门限定。

### 11.3 现有内容版本和切片

现有版本、chunk、索引记录应同步补齐：

```text
scope_type = global
department_id = NULL
```

迁移后需要重建或补写 Milvus 元数据，确保 AI 检索能使用部门过滤。

## 12. 错误处理与安全边界

### 12.1 内容保存校验

后端必须校验：

```text
scope_type = global 时 department_id 必须为空
scope_type = department 时 department_id 必须存在且启用
```

如果校验失败，返回业务错误，不允许保存或发布。

### 12.2 部门停用

部门停用后：

- 不允许新账号选择该部门。
- 不允许新内容选择该部门。
- 已有关联数据不删除。
- 该部门下已发布内容是否继续可见，第一版建议保持可见，避免停用部门造成大面积内容突然消失。

如果业务希望“停用部门后内容立即不可见”，需要单独做强提示和批量下线流程，不建议第一版默认这样做。

### 12.3 防止误发布

发布确认必须明确展示：

```text
这条内容将对谁可见
```

尤其是：

- 全公司通用 + full
- 全公司通用 + general
- 限定部门 + full
- 限定部门 + general

这四种组合的影响范围完全不同，必须让管理员发布前看清。

## 13. 非目标范围

第一版明确不做以下能力：

- 多部门账号。
- 部门树和上下级继承。
- 总部/大区/子部门穿透授权。
- 部门管理员。
- 按项目组、客户、区域、岗位标签授权。
- 内容多部门同时可见。
- 部门级审批流。
- 组织架构外部系统同步。
- 员工答题记录按部门统计。
- 管理员后台按部门隔离数据。

这些能力不是不重要，而是会显著提高复杂度。当前先把单部门模型跑稳。

## 14. 后续可扩展方向

当单部门模型不够用时，可按以下顺序扩展：

### 14.1 多部门账号

新增用户与部门关联表：

```text
user_departments
- user_id
- department_id
```

用户可见部门限定内容的规则变为：

```text
content.department_id in 用户所属部门集合
```

### 14.2 内容多部门可见

新增内容与部门关联表：

```text
content_visible_departments
- content_id
- department_id
```

内容范围从“限定一个部门”扩展为“限定多个部门”。

### 14.3 部门树

新增：

```text
departments.parent_id
```

但需要明确：

- 上级是否自动看下级？
- 下级是否能看上级？
- 跨部门负责人如何授权？

这部分必须单独设计，不能默认继承。

### 14.4 部门管理员

新增后台角色或管理员范围：

```text
admin_scope = global / department
```

部门管理员只能维护本部门内容和账号，但这会影响后台所有列表、详情、编辑、发布、题库、未命中问题接口，必须作为单独阶段实现。

## 15. 验收标准

方案落地后，至少需要满足以下验收：

1. 管理员可以创建部门、停用部门。
2. 管理员可以为员工账号选择归属部门。
3. 管理员新建内容时必须选择“全公司通用”或“限定部门”。
4. 限定部门内容必须选择部门，否则不能保存或发布。
5. 全公司通用内容不允许保存 department_id。
6. A 部门员工能看到全公司通用内容。
7. A 部门员工能看到 A 部门内容。
8. A 部门员工不能看到 B 部门内容。
9. `general_user` 不能看到任何 `full` 内容，即使部门命中。
10. `full_user` 可以看到本部门 `general + full` 内容。
11. AI 问答不能命中其他部门内容。
12. MySQL 关键词兜底也不能命中其他部门内容。
13. AI 来源列表不展示无权部门内容。
14. 巩固测试不能抽到其他部门绑定内容的题。
15. 历史版本可追溯发布时的范围快照。
16. 现有内容迁移后默认仍对原有用户可见。

## 16. 推荐实施顺序

建议按以下顺序实现，避免一次性改动太大：

1. 数据库迁移：部门表、用户部门、内容范围、版本范围、chunk 范围。
2. 后端权限工具函数：统一计算用户可见部门和内容等级。
3. 后台部门管理接口。
4. 账号管理增加部门选择。
5. 内容管理增加可见范围选择。
6. 员工端内容列表和详情增加部门过滤。
7. AI 检索 Milvus 和 MySQL 双路径增加部门过滤。
8. 测验题抽题和提交校验增加部门过滤。
9. 前端展示“可见范围”。
10. 自动化测试覆盖跨部门不可见、全公司通用可见、账号等级继续生效。

这个顺序的核心是先把后端硬边界做稳，再调整前端展示。

## 17. 最终建议

第一版应坚持以下边界：

```text
单部门账号
全公司通用内容
单部门限定内容
账号等级继续过滤敏感度
管理员仍为全局管理员
```

不要在第一版引入多部门、部门树、部门管理员或项目组授权。

这样既能解决“不同业务部门内容不应互相可见”的核心问题，又不会把当前 MVP 变成复杂权限平台。等真实使用中出现跨部门、多部门、上级部门查看下级部门等明确场景，再按扩展方向逐步升级。
